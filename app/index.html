How I build with AI

Sixteen years of shipping software is what lets me tell a good AI suggestion from a confident wrong one.

I use AI every day, for reviewing code, exploring unfamiliar APIs, drafting tests and docs, and prototyping before I commit to a design. When I put AI into software, four rules keep it dependable.

  • The model sits behind an interface

    Application code talks to a small, typed abstraction, never straight to a vendor SDK. Models and providers can change without a rewrite.

  • Conversation state is explicit

    Each session keeps its own memory, isolated and thread-safe, so concurrent users never see each other's context.

  • Every call is a remote dependency

    Timeouts, retries and fallbacks. A slow or failed model response degrades one feature; it doesn't take the system down.

  • Outputs are checked, not trusted

    Structured output is validated against a schema before anything acts on it. If it doesn't conform, it doesn't go through.
